# Amazon Build, Ship, Shape — Friction Log

## 1. Mapping a stateful visual-memory system into conversational tools

**Task attempted:** Expose BlackBox's persistent visual memory through an Alexa+-style conversational interface.

**Steps taken:** Identified the smallest stable actions that map cleanly to tools; implemented `where_are_my_keys_tool`, `what_changed_tool`, `what_do_you_know_tool`, and `recommended_check_tool`; exposed them through a Streamable HTTP MCP server.

**Expected result:** A conversational assistant could query BlackBox without bypassing its existing world-state and uncertainty model.

**Actual result:** The tool boundary worked well, but the main design challenge was deciding what should remain deterministic BlackBox logic versus conversational presentation.

**Severity:** Low.

**Workaround used:** Kept perception, provenance, uncertainty, and ranking inside BlackBox, and used the conversational layer only to request and present those structured outputs.

**Suggestion:** More examples of MCP architectures for stateful, non-chatbot applications would make it easier to understand best practices for tools that wrap long-lived world state.

## 2. Alexa+ track development without relying on gated assistant runtime access

**Task attempted:** Build an Alexa+-appropriate interaction for an existing AI system while keeping the submission reproducible for judges.

**Steps taken:** Implemented a self-hosted MCP server and a browser-based Alexa+-style simulator that invokes the same conceptual memory tools.

**Expected result:** A judge-visible conversational experience that demonstrates the integration without requiring private credentials or device-specific setup.

**Actual result:** The simulator route was practical, but it required additional interpretation of how to demonstrate the assistant integration clearly without overstating access to a production Alexa+ runtime.

**Severity:** Medium.

**Workaround used:** Clearly labeled the experience as an Alexa+ simulation and exposed the MCP tool names and outputs directly in the UI.

**Suggestion:** A canonical end-to-end sample showing an Alexa+ simulator connected to a self-hosted Streamable HTTP MCP server would reduce ambiguity for hackathon builders.

## 3. Keeping heavyweight vision inference reliable in a public demo

**Task attempted:** Make the full BlackBox visual-memory experience judgeable from a lightweight hosted environment.

**Steps taken:** Preserved the complete local perception pipeline while using a preprocessed hero-run snapshot for the hosted conversational demo.

**Expected result:** A reliable demo that still represents real BlackBox output.

**Actual result:** This worked well, but it required extra disclosure so judges could distinguish preprocessed inference output from live cloud inference.

**Severity:** Medium.

**Workaround used:** Added explicit UI and README language stating that the hosted demo replays a hero run generated by the full local BlackBox pipeline.

**Suggestion:** Hackathon guidance that explicitly distinguishes acceptable preprocessed demo data from live inference requirements would help teams building compute-heavy AI systems.
